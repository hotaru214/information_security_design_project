# 前端演示说明（答辩现场讲稿）

> 面向场景：你负责讲解前端，并用前端做现场演示。
> 全部按钮文字、页面行为、数字均来自当前代码与当前数据库的实测，可直接照着念、照着点。
> 演示主线：**e_case01 靶场批次**——一次真实入侵（720 条证据）在前端被完整还原成 47 步攻击链的全过程。

## 2. 开场白（30 秒）

> 「前端是整个溯源系统的可视化消费端，五个页面：**Dashboard 总览、攻击时间线、攻击链、分析报告、数据管理**。它只消费后端的 Event V2 统一契约数据，自己不解析日志。下面我用 E 靶场的一次真实入侵——720 条多源证据——演示从导入数据到看到完整攻击链的全过程。」

## 3. 演示场景详解

### 场景 0 · 数据管理页 ——「数据从哪来」（约 1.5 分钟）

**操作**
1. 点顶部导航「**数据管理**」。
2. 指「**已入库批次**」表格：三行批次。
3. 演示上传：把准备好的 1–2 个原始文件（如一个 pcap）**直接拖到「导入新数据」卡片上**，再拖第二个（**多次拖入自动累加**，不会覆盖），列表显示「已选 2 个文件（共 X KB）」。
4. 「批次名称（case_id）」输入 `demo-live`，点「**上传并解析入库**」。
5. 等结果：「批次 demo-live 导入完成：成功 N 条，解析失败 M 条」+ 每个文件的解析器/事件数表格；**顶栏下拉自动出现并切到新批次**。
6. 在「**批次分析（D 关联引擎）**」卡选中 `e_case01`，点「开始分析」→ 显示「批次 e_case01：720 条事件 -> 47 个攻击步骤、K 个节点」。

**讲词要点**
- 「上传是**自动嗅探**的：pcap、Zeek、filterlog、CSV、主机日志不用选类型，后端按内容识别并分发给 B/C 解析模块。」
- 「批次之间用 case_id 隔离，多批共存互不污染——这就是我们的多批次设计。」
- 「这个「批次分析」按钮直接调 D 的关联引擎，N 条事件进、M 个攻击步骤出。」

**指给评委看**：720 / 23,993 / 96 三个批次的「事件数、告警数、时间范围、来源」列；拖拽累加的文件列表。

**可能追问**
- *解析失败会怎样？* → 「逐文件报告成功/失败条数，失败的文件不影响其他文件入库；接口 300 秒超时上限，大文件也能扛。」
- *删批次呢？* → 「每行有删除按钮，二次确认后整批删除，事件和攻击链一起清掉。」（演示时**不要真点**删除）

### 场景 1 · Dashboard ——「全局一眼看穿」（约 1.5 分钟）

**操作**
1. 顶栏「数据批次」下拉切到 **e_case01（720 条）**（页面自动刷新）。
2. 指 4 张统计卡：**分析事件 720 / 异常事件 17 / 涉及主机 / 攻击阶段**。
3. 指主机 chips 条：「涉及主机：」web-server（111 条，红色=有异常）、win10-jump（17）、core-server（4）等，攻击路径上的主机一目了然。
4. 点「**异常事件**」卡片 → 直接跳到时间线并自动带上「仅看异常」过滤。

**讲词要点**
- 「四张卡都可点击，任何一张钻进去都是带过滤条件的时间线——**从统计到明细一键下钻**。」
- 「异常主机标红，攻击路径（web-server → win10-jump → core-server）在主机条上直接看得出来。」

**指给评委看**：720/17 的对比（720 条证据里只有 17 条高置信告警）；三张图的标题「event_type 分布（点击图例/扇区过滤）」「按小时聚合（正常深色/异常红色）」「severity 分布」。

**可能追问**
- *为什么 720 条只有 17 条告警？* → 「告警是高置信度的检测器输出（13 条 T1021 横向 + 4 条 T1190 Web 攻击），其余是防火墙 pass/block 等基线事件。我们**宁可少报也不误报**，检测阈值如实记录——nmap 6 端口低于阈值 10，就没告警，只事件化。」

### 场景 2 · 攻击时间线 ——「每条证据可翻原文」（约 1.5 分钟）

**操作**
1. 导航点「**攻击时间线**」。
2. 演示过滤器：勾「**仅看异常**」→ 剩 17 条；再把「全部主机」切到 **web-server**；演示「全部 event_type」（分组下拉：登录与会话/进程行为/网络行为/文件行为…）和「时间范围」。
3. 点任意一行 → 行下展开**三区证据面板**：① 关键字段（null 字段直接不显示）② detail 中文标签字段（父进程/攻击阶段/MITRE 技术等）③ **raw_log 原始日志（溯源证据）** 深色代码块。
4. 点面板里「**复制 JSON**」→ 整条事件 JSON 进剪贴板。

**讲词要点**
- 「每一行是一条 Event V2 标准事件；点开就是**原始日志原文**——我们承诺『证据可回查』，就是指这个：前端看到的每条告警都能翻到抓包/日志的原文。」
- 「过滤器是五维的：异常、类型、severity、主机、时间范围，顶部实时显示『共 N 条』。」

**指给评委看**：红色告警徽章（远程服务连接 / Web 攻击）；severity≥2 的行有红边；raw_log 代码块。

**可能追问**
- *时区怎么处理的？* → 「全库统一 UTC+8 ISO8601，解析阶段就对齐过（B 侧还修过 rsyslog 的 ISO8601 格式问题）。」
- *raw_log 是改过的还是原文？* → 「原文。Event V2 契约要求缺失即 null、禁止改写，raw_log 存的就是抓包/日志的原始内容。」

### 场景 3 · 攻击链 ——「重头戏，把 720 条证据讲成一个故事」（约 3 分钟）

**操作**
1. 导航点「**攻击链**」。先讲图的整体形态：「**按攻击阶段分列**——每一列是一个 ATT&CK 阶段，攻击从左往右推进」。
2. 指图例条：「节点色 = 攻入该主机的阶段；灰框 = 仅有 IP 无主机映射；**点击节点/边查看证据**」。
3. **悬停任意边** → 边上浮现标签「[序号] 阶段 · T-xxx + 时间」。
4. **点一条关键边**（如 T1190 那条）→ 右侧栏切到「**攻击动作 [i]**」+「**证据事件（N）**」列表。
5. 点列表里的「**证据事件： #id**」chip → 弹出「**事件详情**」modal → 展示该事件的完整字段 + raw_log 原文 → 关闭。
6. 点右侧栏「**← 返回攻击步骤**」回到总览；再点一个节点演示「节点 X 相关事件」。
7. 滚轮缩放/拖拽画布演示一下（`roam` 开启）。

**讲词要点（配合图讲完整故事）**
> 「这条链就是 E 靶场那次入侵的完整还原：攻击机 10.10.10.10 对 Web 服务器发起 **T1190 命令注入**（DVWA，20 步检出）拿下 **web-server**——它被自动标记为**入侵点**，也就是首个被攻破的内网主机；然后 **T1021 SSH 远程服务**跳到 **win10-jump**（13 条横向告警）；再从跳板访问 **core-server** 取敏感文件（T1005 数据收集）；最后 win10 回连 **c2-server** 发 beacon（T1071）。720 条原始证据 → 47 步结构化攻击链，**每一步都挂着 evidence_event_ids，现场点开就是日志原文**——这就是『溯源』两个字在前端的落地。」

**指给评委看**：分列布局的阶段列头；边的悬停标签；modal 里 raw_log 的原文内容。

**可能追问**
- *证据是怎么关联到边上的？* → 「三级策略：优先用 D 引擎给的 evidence_event_ids；没有就用源目 IP 精确匹配；再退到同主机 ±15 分钟时间窗兜底——保证点边必有证据可看。」
- *灰节点是什么？* → 「只有 IP、没有主机名映射的外部地址（比如攻击者的外网 IP），如实显示为灰色，不假装知道它是谁。」
- *节点太多会不会乱？* → 「按阶段分列 + 滚轮缩放 + 点击节点只看该节点相关事件（侧栏最多列 15 条），大图也能操作。」

### 场景 4 · 分析报告 ——「LLM 优先、规则降级，永远有结果」（约 2 分钟）

**操作**
1. 导航点「**分析报告**」。确认「分析范围」是当前批次（e_case01），点「**开始分析**」。
2. 等待约几秒（未配 LLM key，走规则模板，很快）→ 渲染六段：
   **一、攻击路径**（节点→箭头流向图）／**二、攻击概述**／**三、关键证据**（表格：id/时间(UTC+8)/主机/类型/severity/证据说明；**点行跳时间线定位**）／**四、ATT&CK 技术映射**（阶段+T-ID+证据 chip 可点开 modal）／**五、风险等级与处置建议**／**六、多智能体协调过程**（每个智能体卡：职责、状态、输入事件数、耗时、findings）。
3. 指第六段：「智能体状态 **degraded**、findings 写着『LLM 未配置，智能体降级为规则模板』——**系统如实标注自己此刻是规则在分析，不伪装成 LLM**。」
4. 下拉页面到底部第二张卡「**身份溯源（Attribution）**」：溯源状态、攻击者画像、C2 与外联基础设施、观察到的 TTP、APT/TTP 相似度、证据事件。点「重新加载」演示它独立调 `GET /api/attack-chain/attribution`。
5. （可选）点「复制为 Markdown」/「导出报告」→ 下载 `溯源分析报告_YYYYMMDDHHMM.md`。

**讲词要点（本页的核心设计点，务必讲）**
> 「分析接口的工程原则是**永远返回 200**：优先调 LLM（后端多智能体——主机侧、网络侧两个分析智能体并行，再交给关联智能体汇总），LLM 不可用或解析失败就自动降级到九阶段规则模板，`source` 字段如实标注 llm 或 fallback。所以这个页面**断网也有报告**，只是会诚实地告诉你现在是规则模板在说话——我认为对安全产品来说，『如实』比『好看』重要。」

**可能追问**
- *LLM 会不会胡编证据？* → 「两道防线：LLM 返回严格 JSON、解析失败重试一次；返回里引用的事件 id 会**逐个对着数据库校验**，编造的 id 直接丢弃。关键证据表里的每一条都能点回时间线原文。」
- *配了 key 会怎样？* → 「`.env` 三个变量即插即用；LLM 最坏耗时约 2×30 秒（两个智能体并行），前端 60 秒上限，超时会提示『LLM 仍在后端执行』。」
- *身份溯源可靠吗？* → 「页面自己就标了『可观测 TTP 相似度，非确认身份归因』——我们做的是行为指纹与已知 APT 画像的相似度比对，不妄下结论。」

## 6. Q&A 弹药库

1. **数据是真实的吗？** → 双源：E 靶场是我们自己搭的 9 节点环境全程抓包+日志留存的**真实攻击证据**（e_case01）；apt29 / case03 / CTU-13 是公开数据集。前端页脚可切演示模式，那个是明示的内置样例。
2. **Event V2 契约是什么？** → 19 个公共字段 + 数据库 id，8 种 source 枚举，缺失即 null；一次攻击=一个 case_id=全部证据。前端只消费这个契约，所以换数据源前端零改动。
3. **证据可信/可查吗？** → 每条告警都能点开 raw_log 原文；攻击链每步挂 evidence_event_ids；分析报告关键证据表点行直达时间线。三层全部落到原始日志。
4. **LLM 幻觉怎么办？** → 严格 JSON + 失败重试 + 引用事件 id 对库校验（编造就丢）+ 无 LLM 时规则降级且如实标注。
5. **和 Wazuh/商业 SIEM 区别？** → 它们是单源告警平台；我们做**跨源关联+攻击链还原+证据穿透+归因画像**的轻量闭环，且面向教学场景单仓库可复现。
6. **多智能体体现在哪？** → 分析报告第六段：主机侧/网络侧两个分析智能体并行 → 关联智能体汇总；LLM 驱动，失败逐个标 degraded——过程可见、可审计。
7. **为什么 720 条只有 17 条告警？** → 高置信检测器宁可少报不误报；阈值如实记录（nmap 6 端口 < 阈值 10 不告警）；其余证据以事件形式全量可查。
8. **时区/时间对齐？** → 全库 UTC+8 ISO8601，解析层对齐；时间线/报告统一显示。
9. **大批次性能？** → apt29 2.4 万条秒级切换；攻击链 10 秒超时内返回；已识别的优化方向是分页/增量加载（展望里写了）。
10. **演示模式的数据是假的吧？** → 是内置样例，且徽标明示「演示模式（手动开启，数据为内置样例）」；Live 模式永不回退假数据。
