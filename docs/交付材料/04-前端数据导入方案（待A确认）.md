# 前端数据导入 / 按批切换数据 —— 方案（待 A 确认）

> 提出方：F（前端） ｜ 需求原话："希望能从前端页面直接导入需要用的数据"
> 日期：2026-09-10 ｜ 状态：**待确认，未开工**（涉及后端接口与全链路 case 口径）

---

## 一、需求

演示与验收换数据时，现在只能走命令行（`curl` / `scripts/`）。希望能在页面上直接：

1. 选一个 Event JSON 文件导入；
2. 导入后页面展示的**报告 / 攻击链 / 溯源**都基于这批新数据；
3. 不影响已有数据和现有验收结果。

---

## 二、现状核实（已核对代码，2026-09-10）

| 事实 | 证据 |
|---|---|
| 导入接口**已有** | `POST /api/events/import?case_id=`（批量导入并打 case_id）、`POST /api/events/batch`、`POST /api/hosts/batch` |
| **没有删除/重置接口** | `routers/events.py`、`routers/hosts.py` 只有 POST / GET，无 DELETE |
| 攻击链接口**支持** case_id | `GET /api/attack-chain?case_id=` → `get_events(case_id=…)` |
| **分析接口不支持** case_id | `routers/analysis.py` 的 `AnalysisRequest` 只有 `{host, start, end}`，内部调 `get_events()`（全库） |
| 前端**没有**传 case_id | `api.js` 的 `getAttackChain()` 不带参数；`getAnalysisReport()` 只发 `{host}`；本次新增的 `getAttribution()` 才会带 `?case=` |
| 项目既定约定是**一批一库** | `scripts/reset_import_export.py` 文档字符串："避免多批数据混在同一个库里导致 **D 的关联引擎跨批次串链**" |

> 结论：**"导入"不缺接口，"换数据后只看这批"才是缺口**——因为报告/攻击链不看 case_id，且库里无法清理旧数据。

---

## 三、两条路线

### 路线 A：多批共库 + case_id 全链路贯穿

改动：
1. 后端 `AnalysisRequest` 加 `case_id: str | None = None`，`analyze()` 里改成 `get_events(case_id=request.case_id)`（约 3 行）；
2. 前端 `getAttackChain()` / `getAnalysisReport()` 带上 `?case=` / body 里的 case_id，并在报告页加一个 **case 下拉**；
3. 前端新增"导入"卡片（复用现有 import 接口）。

风险（必须在评审时说清）：
- **跨批串链**：D 的关联引擎按时间与主机连接事件，两批数据在同一库里可能被串成一条假链（`reset_import_export.py` 的注释就是这个原因）；
- 数据累积：重复导入同一批 → 事件翻倍（`id` 重新分配），证据 `evidence_event_ids` 会指向新 upsert 的记录，旧报告作废；
- `get_events(case_id)` 的现有语义是 `WHERE case_id = ? OR case_id IS NULL`（兼容历史无 case 数据），共库后需确认是否会带入无 case 的旧数据。

### 路线 B（推荐）：一批一库，前端导入即"替换当前批次"

沿用项目自己的约定，**不动 D 的关联引擎**：
1. 后端新增一个**数据集重置接口**（A 侧，约 20 行），语义明确、只影响库文件：
   - `POST /api/datasets/reset`（清空 events/hosts 后导入新批），或
   - `POST /api/events/reset?case_id=`（只清指定批）；
   建议加**二次确认参数**（如 `confirm=true`）与返回统计（删除条数/导入条数），避免误触；
2. 前端报告页加"数据导入"卡片：选 `.json` → 本地校验（19 字段是否齐全、`timestamp` 是否 UTC+8 ISO8601、`source` 是否 6 值枚举）→ 调 import（或 reset+import）→ 成功后重新加载页面数据；
3. 可选：支持 `data/hosts_*.csv` 一并导入（`POST /api/hosts/batch`）。

优点：报告天然只分析当前这批；不触碰 D 的算法；与 `reset_import_export.py` 的做法一致，答辩好解释。

## 四、对比与建议

| 维度 | 路线 A（共库 + case 贯穿） | 路线 B（一批一库 + 重置） |
|---|---|---|
| 后端改动 | AnalysisRequest + analyze（3 行） | 新增 reset 接口（约 20 行） |
| 前端改动 | 传参 + case 下拉 + 导入卡 | 导入卡（含确认与校验） |
| D 模块风险 | **有**（跨批串链） | 无 |
| 数据库风险 | 只增不减，易累积重复 | 明确替换，可预期 |
| 验收影响 | 需重跑报告/攻击链相关用例 | 只影响"导入"这一新功能 |

**建议：路线 B**；若 A 认为 reset 接口有数据安全顾虑，则退化为"**前端只做导入 + 页面明确提示需重启/重置库**"，把重置留在命令行（今天就能用，见下）。

## 六、今天就能用的替代方案（无需任何改动）

换数据走命令行，本质就是"一批一库"：

```bash
# 重置库 → 起后端 → 导入单批数据（含主机）→ 可选导出 EventOut
python scripts/reset_import_export.py --name apt29_day1 \
    --events "data/sample_events/apt29_day1_eventout.json" \
    --hosts data/hosts.csv --port 8000
```

- 报告 / 攻击链 / 溯源随后**全部基于这批新数据**（因为库里只有这一批）；
- 公开数据集现成文件：`data/sample_events/{apt29_day1_eventout.json, ctu13_s2_eventout.json}`；靶场 case01：`e_case01_eventout.json`（+ `data/hosts_e_case01.csv`）。
