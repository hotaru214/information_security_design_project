## 〇、两个 id 千万别混（V2特别说明）

- **`id`**：后端SQLite自动生成的统一事件主键，用于数据库查询、事件关联、D的 `evidence_event_ids`。**输入时不用传、B不产生它**。
- **`event_id`**：原始日志自己的事件编号（Windows 4624/4688、Sysmon 1 等）。网络 PCAP/Zeek 没有原始编号时传 `null`，后端不会用数据库id覆盖它。

## 一、标准事件JSON结构（19字段，键必须全在）

```json
{
  "timestamp": "2020-09-09T21:18:23.627951+08:00",
  "host": "MSEDGEWIN10",
  "source": "windows_evtx",
  "event_id": 4625,
  "event_type": "login_failure",
  "user": "IEUser",
  "process": "chrome.exe",
  "src_ip": null,
  "dst_ip": null,
  "dst_port": null,
  "protocol": null,
  "logon_type": 2,
  "session_id": null,
  "cmdline": null,
  "detail": {
    "substatus": "0xc000006a",
    "substatus_desc": "密码错误",
    "failure_reason": "%%2313",
    "workstation": "MSEDGEWIN10"
  },
  "description": "用户 IEUser 登录失败（交互式登录(本地键盘)，原因: 密码错误）",
  "anomaly_flags": [],
  "severity": 0,
  "raw_log": "<Event xmlns=... （原始XML，截断2000字符）>"

```

## 二、字段说明与约束

| 字段 | 类型 | 可否null | 说明 |
|---|---|---|---|
| timestamp | str | **必填** | 统一UTC+8，ISO8601格式 `YYYY-MM-DDTHH:MM:SS[.微秒]+08:00`（B侧输入带微秒=真实精度，后端标准化为ISO8601） |
| host | str | **必填** | 主机名（Windows取evtx的Computer字段）。D的关联引擎按它join |
| source | str | **必填** | 枚举见下方，6个值 |
| event_id | int | 可null | 原始事件ID；PCAP/Zeek无原始编号时null（见第〇节） |
| event_type | str | **必填** | 枚举见下方，不许私造新词 |
| user | str | 可null | 登录/进程涉及的用户 |
| process | str | 可null | 进程可执行文件名（不含路径） |
| src_ip | str | 可null | 源IP。本地登录=null（Windows原始值"-"）；可能是IPv6 |
| dst_ip | str | 可null | 目的IP，仅Sysmon ID 3和C的网络事件有值 |
| dst_port | int | 可null | 目的端口，仅Sysmon ID 3和C的网络事件有值（4624的IpPort是源端口→detail.src_port） |
| protocol | str | 可null | "tcp"/"udp"，仅Sysmon ID 3和C的网络事件有值 |
| logon_type | int | 可null | Windows登录类型（2本地/3网络/10 RDP...） |
| session_id | str | 可null | `"主机名:LogonId"`；4624生成，4634注销配对成完整会话 |
| cmdline | str | 可null | 命令行（Sysmon ID 1必有；4688需开审核策略） |
| detail | dict | **必填** | 各事件独有字段统一放这里，没有特殊字段传 `{}` |
| description | str | **必填** | 中文一句话描述，前端列表直接展示 |
| anomaly_flags | list | **必填** | 异常预标记规则名数组，无异常 `[]` |
| severity | int | **必填** | 0正常/未标记，1低，2中，3高 |
| raw_log | str | **必填** | 原始XML/日志行片段（≤2000字符），前端"查证据"用 |

**三条硬规矩（V2重申）**：
1. 19个键必须全在；允许null的字段只有：event_id、user、process、src_ip、dst_ip、dst_port、protocol、logon_type、session_id、cmdline。
2. **缺失数据必须传 `null`**，不使用 `"unknown"`、0 或空字符串制造占位值。
3. 时间全部统一 UTC+8；**不再单独增加公共Event字段**。

## 三、source 枚举（6值，V2冻结）

`windows_evtx`（B）/ `sysmon`（B）/ `linux_auth`（B）/ `linux_audit`（B）/ `network_pcap`（C）/ `network_zeek`（C）

## 四、event_type 枚举（按D《Event V2 event_type 规范》冻结）

**登录与会话**：`login_success` / `login_failed` / `logout`
**进程**：`process_start` / `process_end`
**网络**：`network_connection`（B的Sysmon ID 3 + C）/ `dns_query`（C）/ `http_request`（C）
**文件**：`file_create` / `file_read` / `file_write` / `file_modify` / `file_delete`
**注册表**：`registry_set` / `registry_create` / `registry_delete` / `registry_query`
**账户与权限**：`user_created` / `user_deleted` / `user_modified` / `group_member_added` / `group_member_removed` / `privilege_change`
**服务与计划任务**：`service_created` / `service_started` / `service_stopped` / `service_deleted` / `scheduled_task_created` / `scheduled_task_run` / `scheduled_task_deleted`
**待D确认**：`log_cleared`（1102审计日志被清除，ATT&CK T1070.002——B已申请加入枚举，用于Defense Evasion阶段）
> 规矩：小写英文+下划线；同类行为一个固定名；事件独有信息放detail不新增event_type。sudo提权执行（Linux auditd）映射为 `process_start`，sudo信息放detail。

## 五、detail 常用键（A示例的统一命名）

`parent_process`、`file_path`、`registry_key`、`registry_value_name`、`registry_value_data`、`registry_operation`、`src_port`、`hashes`
> detail是开放对象，"例如"非穷举。B实际使用的全部键见《给A的标准事件样例》文档第四节的报备清单。

## 六、给A的接口建议

```
POST /api/events/import        # 请求体=标准事件数组（批量），响应={"imported":N,"failed":M}
GET  /api/events               # 分页查询，供前端
POST /api/db/reset             # 清库（Day3回归测试用）
```
D直接消费后端返回的 EventOut；`evidence_event_ids` 保存数据库内部 `events.id`，后端/前端通过ID反查完整Event和raw_log。
（D原设计字段映射：source_type→source，command_line→cmdline，parent_process/file_path/registry_*→从detail读取）
